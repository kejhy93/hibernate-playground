How it works

Real database

Tests use @DataJpaTest against the Postgres started by ./pg.sh, not an embedded DB. Flyway builds the schema; Hibernate only validates it.

Rolled back

Each test runs in a transaction that is rolled back at the end, so the seed data never changes. Edit the tests freely.

Measured

The base class HibernateLesson exposes statements() (JDBC statement count), sql() (the SQL text) and flushAndClear(). The second-level cache is emptied before every test.

The comments in the tests are the explanation. They walk through each step with the SQL it produces. The console shows every statement with its bind parameters and per-session metrics: statements, JDBC batches, flushes and cache hits. open-in-view is off, so lazy loading outside a transaction fails with an exception.

Setup

./pg.sh start          # Postgres in Podman on localhost:5432
./mvnw test            # run all lessons
./mvnw test -Dtest=Lesson02FetchingTest   # or just one
./mvnw spring-boot:run # start the app and use the REST endpoints
./pg.sh reset          # wipe the database; Flyway recreates it on next start

Migrations live in src/main/resources/db/migration. V1 and V2 create the library, V3 the identity lesson and V4 the inheritance lesson. With ddl-auto=validate, every mapping change needs a migration.

Domain

Publisher 1 ──< Book >── N:M ──< Author     book_author join table, owned by Book.authors
                 │
                 └──< Review                cascade ALL + orphanRemoval, owned by Review.book
  • Book: @Version for optimistic locking, @NaturalId isbn, enum stored as string, lazy @ManyToOne publisher, pooled sequence (allocationSize = 50).
  • Publisher: in the second-level cache (@Cache(READ_WRITE), Caffeine via JCache).
  • Tag: IDENTITY id, with an equals/hashCode that is broken on purpose. Reader: UUIDv7 id, with an equals/hashCode that works with generated ids.
  • Inheritance: Payment (SINGLE_TABLE), LibraryItem (JOINED), Notification (TABLE_PER_CLASS), plus the Money record embeddable and the Auditable mapped superclass.

01

Persistence context and entity states

Lesson01PersistenceContextTest

The persistence context is a map from (class, id) to an entity instance, plus a snapshot of the values each entity was loaded with. Most of what Hibernate does follows from that map: fewer SELECTs, dirty checking and delayed writes.

 new Book()         persist()              detach() / clear()
──────────► TRANSIENT ─────────► MANAGED ─────────────────────► DETACHED
                      find()/query  ▲                               │
                                    └──────── merge() (a copy) ─────┘
  • First-level cache: finding the same entity twice runs one SELECT and returns the same object
  • Dirty checking: modifying a managed entity is enough, no save() needed
  • Dirty checking compares values: setting the same value does not produce an UPDATE
  • Detached entity: changes are no longer tracked and never reach the database
  • merge() copies a detached entity's state onto a managed instance and returns that instance
  • persist(): the id is assigned immediately, but the INSERT waits until flush
  • Auto-flush: a query flushes pending changes first so it sees up-to-date data

Takeaway: after merge(), keep working with the returned object. The argument stays detached.

02

Fetching, lazy loading and the N+1 problem

Lesson02FetchingTest

Lazy associations are loaded when first touched. That saves work when you don't need the data. When you need it for a whole list, you get N+1: mapping 8 books to DTOs takes 11 statements. The lesson shows three fixes that each take one statement, then covers proxies and LazyInitializationException.

11naive findAll() + DTO mapping
1JOIN FETCH
1@EntityGraph
1DTO projection, 0 entities loaded
  • N+1: one query for the list, then one extra query per lazy association touched
  • Fix 1, JOIN FETCH: load books, publishers and authors in a single query
  • Fix 2, @EntityGraph: the same single query, declared as an annotation on the repository
  • Fix 3, DTO projection: select only the needed columns, no entities are loaded at all
  • Lazy @ManyToOne: you get a proxy that knows only the id, and the SELECT runs on first real use
  • getReference() returns a proxy without any SQL; the SELECT runs only if you read its state
  • LazyInitializationException: touching an uninitialized association after the session is gone

Takeaway: load what you need while the session is open. Setting open-in-view or making associations EAGER hides the problem and brings N+1 back.

03

Associations: owning side, cascading and orphan removal

Lesson03AssociationsTest

A bidirectional association has two Java fields but one database representation. The owning side (without mappedBy) is what gets written. The inverse side is a read-only mirror. Cascading is a separate concept: it decides which EntityManager operations are passed on from parent to child.

FieldSideDatabase
Review.bookowningreview.book_id
Book.authorsowningbook_author join table
Book.reviewsinverse (mappedBy = "book")not written
Author.booksinverse (mappedBy = "authors")not written
  • Cascade PERSIST: persisting a book also persists the new reviews in its collection
  • orphanRemoval: a review removed from the book's collection is deleted from the database
  • Owning side: only changes to Book.authors are written, and Author.books (mappedBy) is ignored
  • Cascade REMOVE: deleting a book deletes its reviews and join table rows, but not its authors

Takeaway: never put CascadeType.REMOVE (or ALL) on a @ManyToMany. Deleting one book would delete co-authors of other books.

04

Optimistic locking, bulk updates and JDBC batching

Lesson04LockingAndBulkTest

Every UPDATE on Book checks the version it read. A stale copy is rejected instead of silently overwriting someone else's change:

UPDATE book SET ..., version = 1 WHERE id = ? AND version = 0

The lesson also covers two ways to change many rows at once. They behave very differently from the entity-by-entity approach.

  • Optimistic locking: merging an entity with an outdated @Version throws OptimisticLockException
  • Bulk update: one SQL UPDATE for many rows, bypassing the persistence context and @Version
  • JDBC batching: 45 INSERTs are sent to the database in 3 round-trips instead of 45

Takeaway: a bulk update leaves managed entities stale. A later flush can write the old values back. Use clearAutomatically or refresh(), or run bulk operations first.

05

Entity identity, equals/hashCode and id generation

Lesson05IdentityTest

Inside one persistence context, == is enough. Problems appear when instances from different contexts meet (detached entities, proxies, cached copies) or when a new entity goes into a HashSet before it has an id.

Entityequals/hashCodeId strategyVerdict
Authornone (Object identity)sequencefine until contexts mix
Taggenerated id + getClass()IDENTITYbroken
Booknatural id (isbn)pooled SEQUENCEbest, if a business key exists
Readerid + instanceof, constant hashCodeUUIDv7safe for generated ids
  • No equals override: the same row loaded in two persistence contexts gives two unequal objects
  • Id-based hashCode: persist() assigns the id, the hashCode changes and the entity is lost in a HashSet
  • getClass() in equals: a Hibernate proxy is a subclass, so equals becomes asymmetric
  • Natural-id equals (Book.isbn): stable in every entity state, before and after persist
  • Generated-id equals done right (Reader): no id means equal only to itself, constant hashCode
  • IDENTITY: persist() runs the INSERT immediately, because only the INSERT produces the id
  • SEQUENCE with pooled optimizer: one sequence call reserves 50 ids, which are handed out from memory
  • UUIDv7: ids are generated in Java and time-ordered, so persist() needs no database round-trip

Takeaway: allocationSize must match the sequence's INCREMENT BY. IDENTITY disables insert batching.

06

Second-level cache and query cache

Lesson06SecondLevelCacheTest 
em.find(Publisher.class, 1)
   │
   ▼  persistence context   per session, holds entity OBJECTS
   │ miss
   ▼  second-level cache    per SessionFactory, holds entity DATA, survives the transaction
   │ miss
   ▼  database              SELECT … FROM publisher WHERE id = 1  → put into the cache

The second-level cache is shared across sessions and outlives transactions. Entities must opt in. It suits data that is read often and changed rarely. It's a poor fit for data that other applications or SQL scripts change, because the cache can't see those changes.

  • find() by id: the first session puts the publisher into the cache, and later sessions read it from there
  • Lazy @ManyToOne: initializing a publisher proxy is a load by id, so the N+1 publisher queries become cache hits
  • Queries skip the entity cache: a JPQL query always runs its SQL, even for cached publishers
  • Query cache: a cacheable query's result is reused until a table it reads from changes
  • READ_WRITE: a changed publisher is locked in the cache until commit, then the cache holds the new value
  • Bulk and native updates: Hibernate can't tell which rows changed, so it evicts whole regions

Takeaway: a native UPDATE evicts every cache region unless you declare what it touches with addSynchronizedEntityClass.

07

Inheritance mapping, embeddables and element collections

Lesson07InheritanceAndEmbeddablesTest

There are three hierarchies with the same shape, one per strategy. The main thing to compare is the SQL of a polymorphic query ("give me all payments") against a query for one subclass.

StrategyHierarchyPolymorphic queryUse when
SINGLE_TABLEPayment ← Card, Cashone table, no joinssubclasses add few columns (default)
JOINEDLibraryItem ← Magazine, BoardGameLEFT JOIN every subclass tablesubclasses differ a lot and need NOT NULL
TABLE_PER_CLASSNotification ← Email, SmsUNION ALL of every tableyou almost never query the root
@MappedSuperclassAuditablenot possibleyou only want to share the mapping
  • SINGLE_TABLE: all subclasses in one table, so polymorphic queries need no joins
  • JOINED: a table per class, and polymorphic queries LEFT JOIN every subclass table
  • TABLE_PER_CLASS: a full table per concrete class, and polymorphic queries become UNION ALL
  • Polymorphic find(): loading by the root type returns an instance of the right subclass
  • Embeddable: a value object stored as columns of the owner and compared by value
  • @MappedSuperclass: inherited columns in each entity's own table, filled by @CreationTimestamp/@UpdateTimestamp
  • @ElementCollection as a List: changing one value deletes all rows and re-inserts them

Takeaway: a proxy of a root type is not an instance of the subclass. Use Hibernate.unproxy() before checking instanceof.

REST endpoints

The app exposes the same scenarios over HTTP, so you can watch the SQL log while calling them. These requests do change the database.

curl localhost:8080/books/naive        # N+1: watch the log fill up
curl localhost:8080/books/fetch-join   # same JSON, one query
curl localhost:8080/books/summaries    # DTO projection with average rating
curl localhost:8080/books/1
curl -X PATCH 'localhost:8080/books/1/price?value=12.50'
curl -X POST localhost:8080/books/1/reviews -H 'Content-Type: application/json' -d '{"rating":5,"comment":"Great"}'

PATCH returns the old version. The DTO is built before the transaction commits, and the flush (UPDATE and version bump) happens at commit.
